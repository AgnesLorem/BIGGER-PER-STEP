## Targeted MVP-007 prerequisite: Level unification

- **Reason:** equipment unlock authorization currently uses a Level calculation
  that conflicts with the Player Level, HUD, and avatar scale visible to players.
- **Affected callers:** `SessionService`, `GrowthService`, `GuiController`,
  `ScaleCurve`, `EquipmentService`, and Level-gated portals.
- **Compatibility impact:** retain the existing fourth-root visible progression
  curve and replace only the conflicting `Bigger / 10` path. Existing `Bigger`
  values and fractional growth semantics are unchanged.
- **Tests required:** exercise each real consumer boundary and the Level 5, 10,
  25, 50, 100, 200, and 500 unlock thresholds immediately below, exactly at,
  and immediately above their Bigger requirements.
- **Persistence:** no migration is required. The server continues deriving Level
  from authoritative `Session.Bigger`; client Level is never trusted.
- **Boundary:** this is a targeted prerequisite for MVP-007 unlock correctness,
  not a separate progression feature or economy redesign.
- **Runtime dependency:** `RuntimeRegistry/Sessions.luau` owns bounded per-Player
  equipment request lock/timestamp state so `EquipmentService` does not retain
  mutable authorization state in module-level maps. Session teardown removes it;
  the fields are runtime-only and have no persistence or migration impact.
- **Audit evidence:** two dated reports record Level unification and equipment
  rework without modifying earlier immutable reports.
- **Portal dependency:** `PortalService.luau` already consumes LevelFormula but
  needs the same fail-closed handling for frozen/invalid authoritative sessions.
  Its public API, configured requirement, and successful entry flow are unchanged;
  tests cover spoofed attributes, below/exact boundaries, missing sessions, and
  frozen sessions.
- **Runtime unblock dependency:** optional monetization validation must not stop
  `SessionService`, `GameBootstrap`, or `EquipmentService`. Missing IDs
  remain fail-closed through structured configuration status. The Studio-authored
  `StarterGui.MainHUD` remains presentation-only and controllers must tolerate
  its absence, late clone, and reset without blocking equipment startup.

## Integration Boundary

- `ReplicatedStorage.BiggerShared.Game.Config.UpgradesConfig` defines the 8 upgrades, linear sequence, and unlock/multiplier helper rules.
- `LevelFormula.GetLevelFromBigger(Session.Bigger)` is the single canonical source of Level for unlock validation.
- `EquipmentService` registers in `GameBootstrap.luau` and manages server-side unlock/equip RPC calls and state push via `ReplicatedStorage.BiggerEvents.Equipment`.
- `GrowthFormula.GetMultiplier` reads `Session.EquippedGrowthUpgrade` via `UpgradesConfig.GetMultiplier` and computes `equipment × HasDoubleMultiplier × HasVip`.
- `SaveService:QueueProfileSave(Player)` provides non-blocking FIFO save queuing upon successful unlock or equip.
- `EquipmentController` manages client-side equipment state snapshot (`EquipmentState`) and RPC actions.

## Approved Equipment Model & Decisions

### 1. Equipment Sequence & Multipliers
- `None`: 1x (virtual default state)
- `Protein`: 1.5x (1 Destruction, Level 5)
- `SilverProtein`: 2x (5 Destruction, Level 10)
- `GoldProtein`: 3x (15 Destruction, Level 25)
- `DiamondProtein`: 5x (30 Destruction, Level 50)
- `GrowthSerum`: 10x (60 Destruction, Level 100)
- `AdvancedSerum`: 25x (120 Destruction, Level 200)
- `TitanSerum`: 50x (250 Destruction, Level 500)

### 2. `None` Semantics
- Virtual equipment state; `UnlockedGrowthUpgrades` does not store `None=true`.
- `EquippedGrowthUpgrade = nil` represents `None`.
- `None` is always available and cannot be unlocked or persisted as a string.
- `Protein` is the first real upgrade and has no persistent predecessor.

### 3. Level Authority
- Unlock validation MUST calculate Level using `LevelFormula.GetLevelFromBigger(Session.Bigger)`.
- Client `Player:GetAttribute("Level")` is for display only and must never be used for authorization.

### 4. Offline Progression & Save Isolation
- Equipment multipliers apply to active gameplay growth ONLY.
- Offline progression retains existing approved entitlement rules. `UpgradesConfig` is NOT imported by `SaveService`.

### 5. Immediate Non-Blocking Save
- Successful unlock or equip calls `SaveService:QueueProfileSave(Player)` to queue a save in the per-UserId FIFO worker without blocking the client remote invocation.
